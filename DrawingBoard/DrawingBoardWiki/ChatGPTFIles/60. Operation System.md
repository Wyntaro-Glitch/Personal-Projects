# 60. Operation System

The application MUST use an operation-based architecture for document mutations.

An operation represents one logical change to the document.

Every operation MUST contain enough information to:

1. Apply the change.
2. Reverse the change.
3. Be stored in undo history.
4. Be transmitted through Socket.io.
5. Be persisted if necessary.
6. Be identified uniquely.

The fundamental structure is:

```text
Operation
    |
    +---- type
    +---- operationId
    +---- timestamp
    +---- userId
    +---- projectId
    +---- payload
    |
    +---- apply()
    |
    +---- inverse()
```

---

# 61. Operation Schema

Use a plain JavaScript object.

```javascript
const operation = {
    operationId: crypto.randomUUID(),

    type: "ADD_STROKE",

    projectId: "project-001",

    userId: "user-001",

    timestamp: Date.now(),

    payload: {}
};
```

The operation itself should remain serializable.

DO NOT store functions inside the operation object.

Incorrect:

```javascript
const operation = {
    type: "ADD_STROKE",

    apply() {},

    inverse() {}
};
```

Correct:

```javascript
const operation = {
    operationId: "operation-001",

    type: "ADD_STROKE",

    projectId: "project-001",

    userId: "user-001",

    timestamp: Date.now(),

    payload: {}
};
```

The operation engine determines how to apply and reverse the operation based on `type`.

# 63. Operation Registry

Create a centralized operation registry.

Example:

```javascript
const operationHandlers = {

    ADD_STROKE: {
        apply(document, operation) {
            // Apply operation
        },

        inverse(document, operation) {
            // Reverse operation
        }
    },

    DELETE_STROKE: {
        apply(document, operation) {
            // Apply operation
        },

        inverse(document, operation) {
            // Reverse operation
        }
    }

};
```

This prevents operation logic from being scattered throughout the application.

---

# 64. Operation Executor

Create a central function responsible for applying operations.

```javascript
function applyOperation(document, operation) {

    const handler =
        operationHandlers[operation.type];

    if (!handler) {
        throw new Error(
            `Unknown operation type: ${operation.type}`
        );
    }

    handler.apply(document, operation);
}
```

---

# 65. Inverse Operation

The inverse of an operation is another operation that reverses its effect.

Example:

```text
ADD_STROKE
     |
     v
DELETE_STROKE
```

Therefore:

```javascript
ADD_STROKE.inverse()
```

should produce:

```javascript
{
    type: "DELETE_STROKE"
}
```

However, the inverse operation MUST contain enough information to identify exactly what should be deleted.

---

# 66. ADD_STROKE

Operation:

```javascript
const operation = {

    operationId: crypto.randomUUID(),

    type: "ADD_STROKE",

    projectId: "project-001",

    userId: "user-001",

    timestamp: Date.now(),

    payload: {

        layerId: "layer-001",

        stroke: {

            id: "stroke-001",

            tool: "brush",

            color: "#000000",

            size: 10,

            opacity: 1,

            points: [

                {
                    x: 100,
                    y: 100,
                    pressure: 0.5
                },

                {
                    x: 110,
                    y: 110,
                    pressure: 0.7
                }
            ]
        }
    }
};
```

Apply:

```text
ADD_STROKE
     |
     v
Find layer
     |
     v
layer.strokes.push(stroke)
```

Inverse:

```text
ADD_STROKE
     |
     v
DELETE_STROKE
     |
     v
Find layer
     |
     v
Remove stroke by ID
```

Implementation:

```javascript
operationHandlers.ADD_STROKE = {

    apply(document, operation) {

        const {
            layerId,
            stroke
        } = operation.payload;

        const layer =
            document.layers.find(
                layer => layer.id === layerId
            );

        if (!layer) {
            throw new Error("Layer not found");
        }

        layer.strokes.push(stroke);
    },

    inverse(document, operation) {

        const {
            layerId,
            stroke
        } = operation.payload;

        return {
            operationId: crypto.randomUUID(),

            type: "DELETE_STROKE",

            projectId: operation.projectId,

            userId: operation.userId,

            timestamp: Date.now(),

            payload: {
                layerId,
                strokeId: stroke.id,

                // Preserve original data
                // in case the inverse itself
                // needs to be reversed.
                stroke
            }
        };
    }
};
```

# 67. DELETE_STROKE

Delete operation:

```javascript
{
    type: "DELETE_STROKE",

    payload: {
        layerId: "layer-001",

        strokeId: "stroke-001",

        stroke: {
            // Complete original stroke
        }
    }
}
```

The original stroke MUST be stored in the delete operation.

This is important.

Do NOT create:

```javascript
{
    type: "DELETE_STROKE",

    payload: {
        layerId,
        strokeId
    }
}
```

without preserving the deleted stroke.

Otherwise the application cannot reliably undo the deletion.

Apply:

```javascript
operationHandlers.DELETE_STROKE = {

    apply(document, operation) {

        const {
            layerId,
            strokeId
        } = operation.payload;

        const layer =
            document.layers.find(
                layer => layer.id === layerId
            );

        if (!layer) {
            throw new Error("Layer not found");
        }

        layer.strokes =
            layer.strokes.filter(
                stroke => stroke.id !== strokeId
            );
    },

    inverse(document, operation) {

        const {
            layerId,
            stroke
        } = operation.payload;

        return {
            operationId: crypto.randomUUID(),

            type: "ADD_STROKE",

            projectId: operation.projectId,

            userId: operation.userId,

            timestamp: Date.now(),

            payload: {
                layerId,
                stroke
            }
        };
    }
};
```

---

# 68. Important Rule: Inverse Operations Must Preserve Data

Every destructive operation must contain enough information to reconstruct what was destroyed.

For example:

```text
DELETE_STROKE
    |
    +-- layerId
    +-- strokeId
    +-- original stroke
```

```text
DELETE_LAYER
    |
    +-- layer
    +-- original layer index
```

```text
MOVE_LAYER
    |
    +-- layerId
    +-- previousIndex
    +-- newIndex
```

```text
RENAME_LAYER
    |
    +-- layerId
    +-- oldName
    +-- newName
```

```text
SET_LAYER_OPACITY
    |
    +-- layerId
    +-- previousOpacity
    +-- newOpacity
```

The operation must contain the **before state** when necessary.

# 71. MOVE_LAYER

Operation:

```javascript
{
    type: "MOVE_LAYER",

    payload: {

        layerId: "layer-003",

        fromIndex: 3,

        toIndex: 1
    }
}
```

Apply:

```text
3 → 1
```

Inverse:

```text
1 → 3
```

Implementation concept:

```javascript
operationHandlers.MOVE_LAYER = {

    apply(document, operation) {

        const {
            fromIndex,
            toIndex
        } = operation.payload;

        const [layer] =
            document.layers.splice(
                fromIndex,
                1
            );

        document.layers.splice(
            toIndex,
            0,
            layer
        );
    },

    inverse(document, operation) {

        const {
            layerId,
            fromIndex,
            toIndex
        } = operation.payload;

        return {
            operationId: crypto.randomUUID(),

            type: "MOVE_LAYER",

            projectId: operation.projectId,

            userId: operation.userId,

            timestamp: Date.now(),

            payload: {

                layerId,

                fromIndex: toIndex,

                toIndex: fromIndex
            }
        };
    }
};
```

The implementation should preferably locate the layer by ID before moving it to protect against index changes caused by other operations.

# 79. Operation-Based Undo Manager

The history manager should store operations.

```javascript
const history = {

    undoStack: [],

    redoStack: []
};
```

When an operation is committed:

```javascript
function commitOperation(document, operation) {

    applyOperation(
        document,
        operation
    );

    history.undoStack.push(operation);

    history.redoStack = [];
}
```

---

# 80. Undo Logic

Undo should:

1. Remove the latest operation from `undoStack`.
2. Generate its inverse.
3. Apply the inverse.
4. Push the original operation onto `redoStack`.

Conceptually:

```javascript
function undo(document) {

    const operation =
        history.undoStack.pop();

    if (!operation) {
        return;
    }

    const inverse =
        createInverseOperation(
            operation
        );

    applyOperation(
        document,
        inverse
    );

    history.redoStack.push(operation);
}
```

---

# 81. Redo Logic

Redo should reapply the original operation.

```javascript
function redo(document) {

    const operation =
        history.redoStack.pop();

    if (!operation) {
        return;
    }

    applyOperation(
        document,
        operation
    );

    history.undoStack.push(operation);
}
```

---

# 82. Important Rule: Do Not Store Only Inverse Operations

The history stack should store the original operations.

Correct:

```text
undoStack

ADD_STROKE
RENAME_LAYER
MOVE_LAYER
```

When undoing:

```text
ADD_STROKE
     |
     v
DELETE_STROKE
```

The inverse can be generated from the original operation.

This keeps the history understandable and makes redo straightforward.

# 85. Real-Time Operations

Socket.io should transmit operations.

Example:

```javascript
socket.emit(
    "document:operation",
    operation
);
```

The server receives:

```javascript
socket.on(
    "document:operation",
    operation => {

        // Validate operation

        // Apply operation

        // Broadcast operation
    }
);
```

Broadcast:

```javascript
socket.broadcast
    .to(projectId)
    .emit(
        "document:operation",
        operation
    );
```

The receiving clients then apply the operation locally.

# 86. Server Authority

For collaborative projects, the server should act as the authoritative operation relay.

Recommended:

```text
Client A
   |
   | operation
   v
Server
   |
   +----> Validate
   |
   +----> Apply / verify
   |
   +----> Persist
   |
   +----> Broadcast
   |
   +----> Client B
   |
   +----> Client C
```

Clients should not blindly trust arbitrary operations received from other clients.

# 87. Operation Validation

Before applying an operation, validate:

```text
projectId exists
user is authorized
layerId exists
strokeId exists
operation type is allowed
payload has required fields
values are within valid ranges
```

Examples:

```text
opacity >= 0
opacity <= 1

scaleX != invalid value

layerId is valid

strokeId is valid
```

Never allow clients to directly submit arbitrary MongoDB updates.

# 88. Operation IDs and Duplicate Prevention

Every operation MUST have a unique:

```javascript
operationId
```

Example:

```javascript
operationId: crypto.randomUUID()
```

The server can use this to prevent duplicate operations.

Example:

```text
Client sends operation
       |
       v
Server receives operation-001
       |
       v
Process operation
       |
       v
Client accidentally resends
       |
       v
Server sees operation-001
       |
       v
Ignore duplicate
```

# 89. Operation Ordering

Operations should contain:

```javascript
{
```


# 90. Undo in Collaborative Editing

Collaborative undo MUST NOT simply remove the last operation globally.

Example:

```text
User A → ADD_STROKE A
User B → ADD_STROKE B
```

If User A presses Undo, the system should undo:

```text
ADD_STROKE A
```

not:

```text
ADD_STROKE B
```

Therefore collaborative undo should be **user-aware**.

Conceptually:

```text
Global Operation History

A1
B1
A2
B2
A3

User A presses Undo

Find latest undoable operation created by A:

A3

Generate inverse:

DELETE_STROKE A3
```

The inverse itself becomes a new operation in the collaborative operation stream.

---

# 91. Collaborative Undo Example

Initial:

```text
A1
B1
A2
B2
A3
```

User A presses Undo.

DO NOT mutate history as:

```text
A1
B1
A2
B2
```

Instead create:

```text
A1
B1
A2
B2
A3
A3_INVERSE
```

Where:

```text
A3_INVERSE = DELETE_STROKE
```

This preserves the global operation history.

# 92. Operation History vs Document State

Keep these concepts separate.

```text
Document State
=
Current result of all operations
```

```text
Operation History
=
Sequence of changes that produced the document
```

Example:

```text
Operations:

ADD_LAYER
ADD_STROKE
ADD_STROKE
SET_LAYER_OPACITY
MOVE_LAYER
```

Result:

```text
Current Document
```

The document can theoretically be reconstructed by replaying the operations.

# 93. Operation Replay

The system should support:

```javascript
function replayOperations(
    initialDocument,
    operations
) {

    const document =
        structuredClone(initialDocument);

    for (const operation of operations) {

        applyOperation(
            document,
            operation
        );
    }

    return document;
}
```

This is useful for:

- Recovery
- Debugging
- Collaboration
- Version history
- Testing
- Conflict investigation

---

# 94. Operation Immutability

Once an operation has been committed, DO NOT modify it.

Bad:

```javascript
operation.payload.newName = "Something Else";
```

after the operation has entered history.

Instead create a new operation.

Operations should be treated as immutable records.

---

# 95. Operation Validation Schema

The application may eventually introduce a dedicated validator.

Example conceptual validation:

```javascript
function validateOperation(operation) {

    if (!operation.operationId) {
        throw new Error(
            "Missing operation ID"
        );
    }

    if (!operation.type) {
        throw new Error(
            "Missing operation type"
        );
    }

    if (!operation.projectId) {
        throw new Error(
            "Missing project ID"
        );
    }

    if (!operation.payload) {
        throw new Error(
            "Missing operation payload"
        );
    }

    return true;
}
```

Do not use TypeScript schemas.

Plain JavaScript validation is sufficient initially.

---

# 96. Operation Design Rule

When creating a new operation, always answer:

```text
1. What changes?
2. What data is required to apply it?
3. What data is required to reverse it?
4. Can the operation be serialized?
5. Can it be sent through Socket.io?
6. Can another client reproduce it?
7. Can it be validated by the server?
```

If these questions cannot be answered, the operation schema is incomplete.

The final architecture should be:

```text
                    DOCUMENT
                        |
                        |
                  OPERATION ENGINE
                        |
             +----------+----------+
             |                     |
             v                     v
          APPLY                  INVERSE
             |                     |
             v                     v
        Document State       Undo Operation
             |
       +-----+------+
       |            |
       v            v
    Renderer     History
       |
       v
    Canvas

Operation
   |
   +----> Socket.io
   |
   +----> Express
   |
   +----> MongoDB
```

The operation engine becomes the central mechanism through which document mutations occur.

# 99. Final Rule for the AI

**Never directly mutate document state from UI components when the mutation represents a user action.**

Instead:

```text
UI Action
    |
    v
Create Operation
    |
    v
Operation Engine
    |
    v
Apply Operation
    |
    v
Document State
    |
    +----> Canvas Rendering
    |
    +----> Undo History
    |
    +----> Socket.io
    |
    +----> Persistence
```

For example, the LayersPanel should NOT directly do:

```javascript
layer.opacity = 0.5;
```

Instead it should create:

```javascript
{
    type: "SET_LAYER_OPACITY",

    payload: {
        layerId,
        previousOpacity: 1,
        newOpacity: 0.5
    }
}
```

and pass that operation to the operation engine.

This ensures that **every meaningful document change is reproducible, undoable, serializable, collaborative, and persistable**.
